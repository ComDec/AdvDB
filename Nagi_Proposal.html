Advanced Database Systems — Fall 2025

0. Purpose & Scope

This proposal outlines the structure, responsibilities, and planned implementation of the RepCRec (Replicated Concurrency Control and Recovery) simulator. The document highlights major modules, the purpose of their primary functions (including inputs, outputs, and side effects), and the end-to-end approach for implementing Serializable Snapshot Isolation (SSI) atop an Available Copies replication strategy. The design targets a lean ten-page footprint as a precursor to the final five-page design document with diagrams.

System Goal. Provide a deterministic, testable engine that enforces serializable snapshot isolation, supports replicated/non-replicated variables, tolerates site failures, and surfaces sufficient instrumentation for grading scripts and debugging.

1. High-Level Architecture

1.1 Component Overview

Execution flow. Parsed commands are dispatched to the TransactionManager, which coordinates transaction state, interrogates site availability, and consults FailureHistory for failure-aware decisions. Sites house VariableCopy instances that expose MVCC read/write primitives.

1.2 Data Placement

  • Variables: 20 logical variables x1 … x20, initialized to 10 * i.
  • Replication: Odd indices host a single copy at site 1 + (i mod 10); even indices are fully replicated across all 10 sites.
  • Failure semantics: Each site maintains an independent MVCC history that is cleared upon failure and reactivated by the Stale Flag protocol on recovery.

2.3 Transaction

  • read(var) — add variable to read_set.
  • write(var, value) — stage value in private workspace.
  • record_write_site(site, ts) — remember first write timestamp per site.
  • set_waiting(var, op) / set_active() — manipulate WAIT state and deferred operation tuple.
  • commit(ts) / abort() — finalize transaction lifecycle.

2.4 Site

  • initialize_variables() — instantiate VariableCopy objects following placement rules.
  • fail() — mark DOWN, reset each variable’s snapshot history.
  • recover() — mark UP, reapply Stale Flag protocol.
  • write_variable(var, ts, value) — push committed value into replica.
  • dump() — format per-site snapshot for logging.

2.5 VariableCopy

  • write(commit_ts, value) — append version pair, mark readable.
  • read_snapshot(snapshot_ts) — return most recent version predating snapshot_ts.
  • reset_snapshot_history() — collapse history to latest value after failure.
  • set_stale() / set_readable() — toggle read availability post-recovery.

3. Concurrency Control Plan

3.1 Serializable Snapshot Isolation

Validation steps.

  1. First Committer Wins: Compare staged write_set against committed writers whose commit timestamp exceeds the candidate’s start_timestamp.
  2. Dangerous structure detection: Maintain RW incoming edges for each committed transaction; if the candidate has an incoming edge from Tk and Tk already has an incoming RW edge, abort to avoid cycles.
  3. Replica failure check: Inspect site_write_times versus failure_history; any failure occurring after the transaction wrote a site forces an abort.

3.2 Available Copies Writes (ROWAA)

Writes are buffered until commit; upon validation success the manager propagates each value to all currently up replica sites while logging the site list for transparency. Transactions wait immediately if their target site (non-replicated variable) is down or if no readable replica exists (replicated variable). The waiting operation is replayed after recovery via the waiting_operation hook.

3.3 Failure & Recovery Handling

  • Failure: Site resets MVCC state; TM aborts transactions that read non-replicated variables on the failed site; waiting writers remain pending.
  • Recovery: Non-replicated variables are readable immediately; replicated variables flip to stale until a fresh commit writes them; TM replays waiting operations.
  • Durability assumption: The simulator assumes commit is atomic per site; partial commits are not modeled.

6. Risks & Mitigations

  • Complex SSI cycles: Danger structure tracking could miss multi-edge scenarios. → Maintain per-transaction RW ancestry and add logging for debug.
  • Recovery correctness: Ensuring stale flags reset properly. → Augment tests with staged recoveries before and after writes.
  • Output compliance: Dump/log formats must align with grader expectations. → Keep outputs deterministic and align with provided examples.

7. Summary

The proposed architecture already demonstrates the target algorithms in code while leaving room for tightening SSI edge detection, expanding tests, and refining documentation. By centralizing concurrency control in TransactionManager, encapsulating MVCC logic in VariableCopy, and enforcing ROWAA semantics with explicit site tracking, the simulator satisfies RepCRec requirements and remains extensible for later experimentation.
