RepCRec: Replicated Concurrency Control and Recovery System

Advanced Database Systems Project

Executive Summary

RepCRec is a distributed replicated database system implementing Serializable Snapshot Isolation (SSI) with Multi-Version Concurrency Control (MVCC) across 10 distributed sites. The system manages 20 variables with selective replication, demonstrating key distributed database concepts including the Available Copies algorithm, optimistic concurrency control, and fault-tolerant recovery.

Key Features: - Serializable consistency guarantees - MVCC for lock-free reads - Replicated data with failure tolerance - Optimistic concurrency control

1.2 Data Distribution

  • Variables: 20 variables (x1-x20), initial value = 10×i for xi
  • Replication Strategy:
  • Odd variables (x1, x3, ..., x19): Non-replicated, stored at site 1 + (i mod 10)
  • Even variables (x2, x4, ..., x20): Fully replicated across all 10 sites

2.2 Multi-Version Concurrency Control (MVCC)

Objective: Enable concurrent reads without blocking writers using version snapshots.

flowchart TD Start([Transaction T starts<br/>start_ts = 5]) --> Read[Read variable x] Read --> Check{Variable in<br/>write_set?} Check -->|Yes| ReturnWrite[Return write_set value] Check -->|No| GetVersions[Get version_history<br/>from site] GetVersions --> FindVersion{Find version where<br/>commit_ts < start_ts} FindVersion -->|Found| ReturnValue[Return snapshot value] FindVersion -->|Not found| ReturnInitial[Return initial value] ReturnWrite --> End([Return value]) ReturnValue --> End ReturnInitial --> End style Start fill:#90EE90 style End fill:#90EE90

Key Algorithm:

def read_snapshot(self, snapshot_timestamp: int) -> int:
    snapshot_value = self.version_history[0][1]  # Initial value
    for commit_ts, value in self.version_history:
        if commit_ts < snapshot_timestamp:
            snapshot_value = value
        else:
            break
    return snapshot_value

Complexity: O(V) where V = number of versions

2.3 Serializable Snapshot Isolation (SSI)

Objective: Provide serializability while maintaining snapshot isolation benefits.

flowchart TD Start([Transaction T calls end]) --> CheckWW{Check Write-Write<br/>Conflict} CheckWW -->|Conflict| Abort1[ABORT T<br/>First Committer Wins] CheckWW -->|No Conflict| CheckRW{Check Read-Write<br/>Conflict} CheckRW -->|Conflict| Abort2[ABORT T<br/>Dangerous Structure] CheckRW -->|No Conflict| AssignTS[Assign commit_timestamp] AssignTS --> ApplyWrites[Apply writes to all<br/>available sites] ApplyWrites --> Commit[COMMIT T] Abort1 --> End([Complete]) Abort2 --> End Commit --> End style Start fill:#90EE90 style Abort1 fill:#FF6B6B style Abort2 fill:#FF6B6B style Commit fill:#51CF66 style End fill:#90EE90

Validation Rules:

  1. Write-Write Conflict: If T2 commits after T1 starts and both write to the same variable → T1 aborts
  2. Read-Write Conflict: If T2 commits after T1 starts and:
  3. T2 wrote what T1 read, OR
  4. T2 read what T1 wrote → T1 aborts

Complexity: O(T·N) where T = committed transactions, N = variables

2.5 Failure Recovery (Stale Flag Protocol)

flowchart TD Start([Site recovers]) --> MarkUP[Mark site status UP] MarkUP --> Iterate[Iterate variables] Iterate --> CheckRep{Variable<br/>replicated?} CheckRep -->|Yes| MarkStale[Mark is_readable = False<br/>Stale flag] CheckRep -->|No| MarkReadable[Mark is_readable = True<br/>Immediately usable] MarkStale --> NextVar{More<br/>variables?} MarkReadable --> NextVar NextVar -->|Yes| Iterate NextVar -->|No| AbortActive[Abort transactions<br/>that accessed failed site] AbortActive --> WakeWaiting[Wake waiting transactions] WakeWaiting --> End([Recovery complete]) style Start fill:#90EE90 style MarkStale fill:#FFD93D style MarkReadable fill:#51CF66 style End fill:#90EE90

Recovery Logic: - Non-replicated variables: Immediately readable (only copy exists) - Replicated variables: Marked stale until next committed write updates them

6. Theoretical Foundations

6.1 Consistency Guarantees

  • Serializability: Execution equivalent to some serial order
  • Atomicity: Transactions commit or abort entirely
  • Consistency: Invariants maintained across commits
  • Isolation: Transactions see consistent snapshots
  • Durability: Committed data persists
